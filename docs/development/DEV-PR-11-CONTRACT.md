## Appendix A. Acyclic content identities and evidence reuse (FM24)

Authority direction is strictly `RefinementBinding → upper_revision_ref → lower/native claim locators`; an upper object never contains a binding-ref collection, a qualification badge, a reverse index or any digest depending on its own eventual binding. `claim_slots` are named canonical projections containing exact lower statement/direction/context/version/quantifier/witness locators and explicit open conditions. Their canonical fingerprint excludes prose/display and all reverse associations. Binding payload includes `upper_revision_ref`, `upper_claim_slot`, `claim_fingerprint`, exact selected native support IDs, consumer requirement/policy and applicability/invalidation refs. Its hash covers those bytes. The server-derived reverse index maps upper ref/slot to exact binding refs at the selected journal commit, and is disposable/replayable. Other upper dependencies must already resolve or be topologically ordered; cyclic content-addressed dependencies reject. Organizational cycles use stable object IDs explicitly labeled navigation only, never unresolved future exact hashes or scientific evidence.

Serializable creation flow: (1) load already exact native statement/context/support refs S/C/E; (2) canonicalize a Module payload with slot `result`, S/C, direction, ordered quantifier/witness locators, target/D0 and display text; calculate body digest and revision `U1`; no binding list exists in these bytes; (3) canonicalize Binding `B1` referring to U1/result and the recomputed claim fingerprint plus E and frozen requirement; (4) a delta contains the immutable bodies U1 and B1 and expected selected refs, in that dependency order; after atomic application, reverse association is derived from the committed binding. No final hash needs to be solved recursively. Opaque capture/operation IDs are generated before canonicalization and never use the enclosing event's eventual digest.

Display revision: create U2 with predecessor U1, unchanged exact slot fingerprint and changed display fields. The closed delta may contain `same_claim_links=[{old_upper_ref:U1,new_upper_ref:U2,old_slot:"result",new_slot:"result",claim_fingerprint:F,source_binding_ref:B1}]`. These links are separate event facts, not fields recursively hashed into U1/U2/B1. All refs exist before hashing the delta. Validate scope, same stable object lineage, exact canonical slot equality (including every context/version/direction/quantifier/witness field), and current support/withdrawal state. Read U2 returns `binding_target=U1`, `displayed_upper=U2`, `reuse_link_ref=<exact event locator>` and re-evaluated qualification. It never says B1 directly binds U2. History preserves U1, U2, B1 and the mapping; alternatively a new B2 may explicitly bind U2. A changed mathematical slot cannot use this mapping and needs a new binding. ReaderProfile changes do not mutate claim identity.

Reject a submitted U1 containing `refinement_refs:[B1]` while B1 refers to U1, even if the client supplies purported hashes, placeholders or a fixed-point claim; unknown schema fields and unresolved/circular exact refs fail. Also reject U2 reusing B1 without a valid explicit link, mismatched witness/direction/context or an invented old binding target. This rule is distinct from mathematical cycle testing FM06.
