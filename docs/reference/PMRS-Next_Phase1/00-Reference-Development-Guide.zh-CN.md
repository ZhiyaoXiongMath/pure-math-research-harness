## 1. 核心结论与设计决策

PMRS 宜定位为：

> **面向纯数学研究的、证据约束的分层多智能体研究 harness。**  
> A domain-specific, evidence-grounded multi-agent research harness.

这个完整表述是本指南建议的产品定位，并非声称它是一个已有统一定义的学术门类。

新版的主要变化不是“再加一个总结文件”，也不是“把网页换成聊天窗口”，而是建立以下可持续运行的闭环：

```text
数学知识模块与问题骨架
        ↓
MAIN 识别可连接的机制和最有价值的未知箭头
        ↓
有明确职责的阶段任务进行证明、构造、反驳或适用性研究
        ↓
详细数学证据 + 对骨架的精确修订建议
        ↓
必要的独立检查、证据接纳与依赖更新
        ↓
新的数学骨架和下一次研究选择
```

“快理解”负责决定值得研究什么以及为什么；“慢理解”负责把具体数学主张落实为可以检查的内容。两者需要双向反馈，不能只有从摘要跳到长文的单向链接。

### 1.1 本指南建议确定的决策

| 决策 | 内容 |
|---|---|
| 产品交互 | 完全取消 PMRS 自建 Web UI 与看板；保留无界面的研究内核、CLI 与必要的本地工具接口。 |
| 科研主控 | 每个 TRH/FDH 实例保留唯一逻辑 MAIN；MAIN 根据数学证据动态选路，不改成宿主固定流水线。 |
| 人机讨论 | 新 Codex 会话默认作为独立观察／讨论角色，读取一致快照；不取得 MAIN 身份或直接写入科研状态的权限。 |
| 认知层 | 增加第一类、可版本化的数学模块、连接机制和研究骨架，而非只增加摘要缓存。 |
| 证据层 | 保留六类原生科研记录及其精确来源、支持、审查与撤销机制。 |
| 角色分工 | MAIN 主要做数学战略推理；阶段任务主要做具体推导与验证，并交付对快理解层的修改。 |
| 运行后端 | 先实现 Codex-first 的无界面版本，同时把领域内核与后端分离；DeepSeek Harness 作为可验证的适配选项。 |
| 迁移边界 | 不原地修改旧的暂停科研项目，不因为软件升级而恢复 Goal、追加预算或改变数学结论。 |

### 1.2 不做什么

不把所有数学压缩成一张巨图；不要求探索前先写完一部教材；不把 MAIN 降格为只会分配编号的行政调度器；不以 JSON 合法、引用存在或多人同意来判定数学正确。

不以“全部 agent 使用同一个聊天历史”代替共享知识库；不以删除浏览器界面为理由删除暂停、授权、证据追踪、原始输入输出或报告服务。

## 2. PMRS 属于什么术语范畴

### 2.1 用分层描述代替单选题

| 层面 | 推荐术语 | 在 PMRS 中的含义 |
|---|---|---|
| 整体产品 | Research-agent application / domain-specific research harness | 面向纯数学研究的完整应用。 |
| 科研组织方式 | Research protocol / dynamic research policy | TRH、FDH 的职责、判断准则、回流与交付规则。 |
| 多智能体组织 | Multi-agent orchestration / hierarchical agent architecture | MAIN 选路，具体任务执行，独立任务审查，结果合流。 |
| 知识组织 | Evidence-grounded research memory / mathematical knowledge management | 快理解骨架、详细论证、来源、支持和版本关系。 |
| 执行基础设施 | Agent runtime / agent harness | 会话、模型调用、工具、任务、恢复、权限和执行事件。 |
| 可安装入口 | Agent skill / plugin | 方法说明、角色提示、工具说明、脚本与资产的打包入口。[E10] |
| 界面 | Client / presentation layer | CLI、Codex 对话入口；Web UI 只是此前的一种表现形式。 |

OpenAI 对 Codex harness 的描述重在 agent loop 和执行逻辑；Anthropic 则用预定义控制路径与模型动态决策来区分 workflow 和 agent。[E1][E2]

因此，PMRS 不是“不能叫 workflow”，而是只称 workflow 容易让协作者误以为它是 P1 到 P14 的固定流水线。只称 skill 又容易忽略运行时、持久状态和证据资格。

**对外沟通建议：**

> 我在开发一个面向纯数学研究的 multi-agent research harness。它采用 MAIN 加定向研究任务的分层组织方式，知识库分为可探索的数学骨架和可追溯的详细证据；科研协议包括目标证明型 TRH 和命题发现型 FDH。

### 2.2 值得研究的相邻范式

最接近本次设计诉求的经典软件思想是 **blackboard architecture**：不同专门能力围绕共享的问题状态贡献局部成果，控制策略决定下一步启用哪一种能力。它可以帮助思考 MAIN、专家任务与共享知识库的关系，但不能自动提供数学可靠性。[E7]

**Hierarchical planning / HTN planning** 有助于研究目标、子目标、分解和执行职责；不应因此把开放数学探索强制变成预先列尽的有限任务树。[E8]

**Context engineering** 有助于思考不同角色如何获得恰当而非全部的上下文；**provenance** 有助于追踪一个主张依赖哪个来源、任务和版本。这两者都不能代替数学论证。[E6][E9]

建议检索的组合包括：

```text
agent harness architecture
multi-agent research orchestration
blackboard architecture knowledge sources control
hierarchical planning abstraction refinement
context engineering long-running agents
scientific knowledge representation provenance
human-in-the-loop agent steering
agent evaluation information contamination
```

这里的“快理解／慢理解”最好称为 **战略性数学抽象／详细数学论证**，不要直接等同于心理学意义的 System 1／System 2。“快”指调用和理解的层级，不意味着低强度推理或粗心判断。

## 3. 对 4.2.2-preview 的定向审阅

### 3.1 已经有的能力，应当保留

| 现有机制 | 静态依据 | 对新版的价值 |
|---|---|---|
| TRH/FDH 独立持久 MAIN，动态派工 | README、架构文档、`strategy.py`、TRH 方法手册 | 不需要重新建立科研主控模型。 |
| 路线机制、失败综合、前后缺口、重启条件 | 架构文档、TRH 方法手册、`research_audit.py` | 已有战略记忆的基础，不能说完全没有快理解意图。 |
| 六类不可变记录、精确前提与开放条件 | `knowledge.py` | 是下层证据基础，应保留。 |
| 指导原文、版本、实际送达与采用记录 | 架构文档、`research_audit.py` | 支持安全的人机指导，不必绕过内核。 |
| 项目助手与独立会话、预算、报告上下文 | `assistant.py` | 观察／讨论角色已有可重用服务。 |
| CLI 访问共享应用服务 | `cli.py` | 无界面化不是从零开始。 |
| 独立报告、精确快照、版本与修订检查 | `reports.py` | 不应因取消网页而重写整个报告系统。 |

以上只说明相应文档／代码机制存在；不表示每种行为都经过本次运行验证。[R2–R10]

### 3.2 尚未充分落实的部分

**第一，战略记忆不等于可调用的数学模块体系。**

路线说明和检查点可以回答“我们刚才做了什么”，但还需要回答“有哪些可复用机制、输入是什么、输出是什么、哪些连接已经成立、下一步最该检验哪个接口”。

**第二，现有知识类型与阅读层次是两条不同的轴。**

`Context/Statement/Argument/...` 描述内容的数学身份；“快／慢”描述表达粒度与使用方式。一个短而精确的 Statement 可以是快理解模块的核心，一个 Argument 可以支撑一条路线箭头。不能仅凭六类名称就断定其内容全部是慢数学。

但仅有这些类型，也不会自然长出适合 MAIN 的数学骨架。

**第三，所检查的知识搜索是有界正文前缀导航。**

`knowledge_access.py` 中，导航读取每个可见正文的前 `2048` 字节，索引上限为 `4096` 个引用，使用词项匹配，并明确标注其覆盖只是前缀导航。它不是成熟机制的输入／输出检索，也不是对全体正文的完整语义理解。[R6]

这不证明系统所有其他读取方式都无效，但足以说明：不能把这个搜索入口当作已经完成的快数学知识服务。

**第四，MAIN 与定向研究任务的分工还没有按本次理念收紧。**

当前 TRH 手册允许 MAIN 自己做数学，并要求新的科研推导提供完整原生 Argument。这个规定重视证据，但没有把 MAIN 的常态职责限定为数学战略探索。[R4]

**第五，没有从本次查看范围中确认以下完整产品契约：**

```text
知识模块 → 项目适用性 → 精确 transition → 定向任务
      → 详细结果 → 对模块／transition 的版本化修订
```

这是本指南建议补齐的核心。应说“尚未确认这一闭环被充分落实”，而不是未经全仓库及真实输入输出审计就宣称“完全没有实现”。

### 3.3 一个需要集成测试的静态疑点

`strategy.py` 使用 `research_routes`；所查看的 `knowledge_access.search()` 路线导航分支遍历 `routes`、`strategy_routes`、`attempt_accounts`、`incidents`。[R5][R6]

这可能使某个通用搜索入口遗漏新版路线集合。需要测试真实的路线写入与搜索闭环。其他 MAIN 输入通道可能仍然传递路线，所以不能据此断言 MAIN 看不到任何路线。

### 3.4 不得扩大实验结论

仓库明确把公开版本标为 candidate22 预览，说明唯一真实 HSC TRH 实验的数学状态仍为 OPEN，且后来由用户暂停；没有把 FDH、SURVEY 或全部行为标为实测通过。[R2][R3]

本指南没有检查那次实验的私人原始材料。因此，本次不能给“科研效率已经提高”“所有权限隔离已经正确”或“MAIN 实际不会重复失败路线”作运行层保证。

## 4. 目标架构：取消网页，而非取消内核

### 4.1 建议的结构

```text
研究者
  │
  ├── Codex 观察／讨论会话
  │      ├── 读取固定快照、数学骨架、证据和报告
  │      ├── 在自己的讨论空间中形成想法
  │      └── 提交提案；获得相应用户授权后提交操作性指导
  │                         │
  │                    持久指导收件箱
  │                         ▼
  └── 直接控制命令 ──→ PMRS 控制与证据内核
                            │
                     每实例唯一 MAIN
                            │
              数学骨架与候选机制的战略探索
                            │
                定向研究任务／独立审查任务
                            │
              详细证据 + 快理解层修改提案
                            │
                     接纳与依赖更新
                            ▼
       共享知识库：数学骨架 ↔ 精确证据；报告与历史

下层执行后端：Codex 适配器，或经验证的 DeepSeek Harness 适配器
```

内核做确定性的权限、版本、证据结构和执行状态管理。它不替 MAIN 选择数学路线，也不自称能通过 schema 校验判断一个新证明在数学上正确。

### 4.2 “Codex 内部驱动”的准确含义

建议理解为：用户在 Codex 中交互，MAIN 与阶段任务由 Codex 或其他受支持运行时执行，PMRS 提供领域工具和持久知识。

不建议理解为：把 PMRS 全部改写为 Codex 源码补丁，或把全部功能塞进一个无限增长的聊天线程。

**Headless 不等于 hostless。** 即使没有网页，仍需要少量宿主职责：可靠接收完成事件、保存状态、控制新调用、恢复会话、执行暂停与权限校验。

这一宿主可以是前台受控进程，也可以在用户明确启动后作为本地服务运行；它不是第二个科研 MAIN。

### 4.3 程序边界

| 组件 | 可以做 | 不可以做 |
|---|---|---|
| MAIN | 选择机制、安排职责、比较结果、提出与调整路线 | 改写原目标、伪造用户授权、把计划直接标成证明 |
| 研究任务 | 在明确职责内自主选择数学方法，给出详细结果和骨架修订建议 | 未经 MAIN 接纳就扩大项目范围或启动另一套科研主控 |
| 独立审查任务 | 在冻结的允许输入内检查指定数学问题 | 读取被禁止的历史判词、借由快理解摘要绕过隔离 |
| 观察／讨论任务 | 读取、解释、讨论、准备提案 | 直接覆盖正式知识库（canonical KB）、修改预算、擅自恢复 Goal |
| 内核 | 验证身份、授权、版本、引用、资格规则，提交已接纳变更 | 自动凭阶段编号选择数学路线或把模型自信当证明 |
| 后端适配器 | 执行、通信、记录实际支持的调用状态与用量 | 宣称未观测的调用成功，静默降低模型或权限要求 |

## 5. 知识库：两层数学表示，一条可检查的落实关系

### 5.1 保留下层，建立上层

下层继续保留：

```text
Context / Statement / Argument / Example / SourceEvidence / Assessment
```

上层不按“文档长度”划分，而按数学使用方式组织：

| 上层对象 | 应回答的问题 |
|---|---|
| Knowledge Module，知识模块 | 给定什么，可以得到什么？这个工具的机制与边界是什么？ |
| Transition，连接机制 | 为什么这几个模块能够接起来？尚缺哪些接口？ |
| Research Map，研究骨架 | 原目标、路线、替代路线和关键缺口如何组织？ |
| Frontier / Probe，探索前沿与判别尝试 | 哪个未知问题的解决最可能改变当前研究选择？ |

第一版可以用少量 Markdown 正文加结构化元数据实现；不要求四种对象分别引入复杂数据库系统。

### 5.2 上下层并非两套彼此竞争的事实库

上层对象可以有自己不可变的修订记录，因为“如何组织数学”本身包含有价值的研究判断。

但上层的数学资格必须依赖下层证据，而不能自我认证：

$$
\text{上层主张在指定范围内的 checked 资格}
\Longrightarrow
\text{绑定明确的下层依据、范围和审查资格}.
$$

这里的箭头是产品约束。它不意味着软件内核能够自动证明所有非形式化数学。

研究图的“应该先做什么”属于战略判断；“A 在这些条件下推出 B”属于数学主张。两种内容可以出现在同一张路线卡里，但必须分别标识。

### 5.3 RefinementBinding：关键不是摘要，而是落实关系

建议增加轻量的 `RefinementBinding`，记录上层某个精确主张如何落实到下层。

最少需要：上层对象及修订、被支持的具体主张／箭头、精确 Context、支持记录与版本、开放条件、必要的审查范围、失效依赖。

不要只记录“这条路线引用了论文 X”。需要知道论文 X 支持的是哪一步、适用范围是什么，以及从论文的对象迁移到本项目对象是否另有待证接口。

```yaml
# 拟议结构；不是现有 PMRS schema，也不是实际证据。
refinement_id: example:refinement-1
upper_ref: example:transition-1@v2
claim: "在共同背景 C 下，A 与 B 足以推出 G"
context_refs: [example:context-C@v1]
support_refs: [example:argument-7@v3]
review_refs: [example:assessment-4@v1]
open_conditions: [example:condition-uniformity@v1]
invalidates_on:
  - example:context-C@v1
  - example:argument-7@v3
```

实际开发应尽量复用已有支持、范围和失效系统；不要另写一套弱化版本的 proof authority。

## 6. 如何建立真正的“快理解”

### 6.1 一个知识模块应当可以被调用

“椭圆理论”“紧性”“代数几何方法”太宽；孤立的文献编号又太窄。一个合格模块应能让 MAIN 判断是否可用，并让阶段任务知道要核对什么。

建议正文采用以下短模板：

```markdown
# 模块：一个具体可调用的数学机制

## 用途
它解决哪一种障碍？本项目为什么可能需要它？

## 输入与输出
[精确对象与必要条件]  ==>  [精确可用结论]

## 核心想法
用几句话及关键公式说明为什么这个机制有效。

## 适用边界
哪些条件不可省？哪些相近但不同的情形不能直接套用？

## 本项目中的位置
对应哪条路线、哪个输入缺口或哪个输出需求？

## 证据与状态
模块本身依据；本项目适用性；待检验接口；展开到详细证据的引用。
```

机制的输入／输出不能因为“快理解”而省掉决定可用性的假设、参数依赖或量词。

### 6.2 好的模块切分以“决策边界”为依据

应当拆分模块的典型情况是：一个独立条件决定其能否使用；一个接口可能单独失败；一个机制能够在其他路线复用。

不应为了文件粒度整齐，把每个代数变形、每个局部定义和每句话都拆成独立知识点。那会使 MAIN 在导航成本中失去数学整体感。

**判断标准：**读完该模块后，能否提出一个具体、可执行、可能改变路线选择的问题？如果不能，模块可能仍然只是主题标签或摘要。

### 6.3 读者基础必须显式，而不是一句“面向博士生”

默认读者具有数学本科通用基础和相关方向博士低年级基础。但这个描述不足以唯一确定可省略哪些内容。

建议使用一个可修订的 `ReaderProfile`，区分：

| 部分 | 内容 |
|---|---|
| 通用基础 | 允许不重复讲解的概念与基本方法，尽量列出实际模块而非学校／年级标签。 |
| 专项入口 | 本领域必须知道、但非本领域读者未必熟悉的少量关键模块。 |
| 本项目特有内容 | 新定义、特殊归一化、特殊接口、当前研究假设；不得默认为已知。 |
| 展开策略 | 哪些模块先给直观解释，哪些附精确定理，哪些直接链接详细论证。 |

读者“知道这个定理”是解释策略，不是证明资格。ReaderProfile 的变化不能自动改变 Statement 的数学内容或支持状态。

同一组下层证据可以导出不同读者深度的入口视图。MAIN 的工作视图也不必和给人写的讲义逐字相同。

### 6.4 先建小骨架，再按障碍生长

初始化只需要原目标、关键背景、第一批候选模块和明显未知连接。没有确证的模块可以作为待核实线索保留。

随后按以下循环生长：

```text
原目标要求什么输出？
    → 哪种成熟机制能产生这个输出？
    → 它要求什么输入？
    → 现有结果是否真的给了这些输入？
    → 缺口能否通过一个定向尝试区分可行与不可行？
```

这不是要求先读完全部文献，也不是限制 MAIN 只能在旧模块里拼装。MAIN 可以提出新中间量、新对象、新机制和新连接，但必须标为探索性内容，并指明其可检验部分。

### 6.5 区分两个图

**读者入口图**组织理解顺序：先知道什么，才能快速理解当前想法。

**证明依赖图**组织数学依赖：哪个结论实际需要哪些前提、推导和共同条件。

二者不应混为一谈。一个适合讲解的类比不一定是证明前提；证明中需要的一个技术事实也未必值得占据总览首页。

### 6.6 快理解质量的实际检验

不要用“摘要不超过多少字”作为主要验收。应让另一个具有目标背景的读者或测试角色回答：

1. 目标究竟是什么？哪些背景不可改变？
2. 核心知识模块分别输入什么、输出什么？
3. 哪一条连接是关键思想，为什么不是机械套用？
4. 哪些已检查，哪些有条件，哪些只是假设？
5. 下一项定向尝试是什么，它的不同结果如何影响路线？

如果这些问题答不出来，即使总览语言流畅，也不能认定快理解层合格。

### 6.7 不要求重新证明全部成熟数学

对已有成熟工具，可以以精确来源、明确可信边界和必要的适用性核对作为调用依据；不要求每个项目重新证明全部本科定理。

但“模型记得有这么一个定理”只能先作为检索或核实线索。越接近项目关键新连接，越需要核对精确条件、版本与迁移论证。基础熟悉程度、文献依据和项目适用性必须分开记录。

不应因某个模块尚未核实而冻结整个探索。它可以保留在待探索层，MAIN 同时安排其他具有充足输入的研究。

## 7. Transition 必须成为可研究的对象

### 7.1 不能只有知识点，没有箭头

研究的困难经常不在 A、B 两个成熟结果，而在“本项目的 A 是否满足 B 的入口”。因此，Transition 不是知识点之间的一条装饰性连线。

它至少应包含：起点／终点、连接类型、关键想法、共同背景、缺口以及检验方式。

| 连接类型 | 含义 |
|---|---|
| IMPLIES | 正向蕴含，必须有相应数学依据。 |
| EQUIVALENT | 双向关系，两方向分别有支持。 |
| CONDITIONAL | 在明确附加条件下成立，条件不得隐藏。 |
| APPLICABILITY | 某方法在本项目对象上是否满足入口条件。 |
| ANALOGY / HEURISTIC | 启发性类比；没有因此获得蕴含资格。 |
| OPEN_TRANSITION | 计划研究的连接，目前不声称成立。 |

必要条件只能作为必要条件。倒推目标时画出的搜索路径，不得被显示成反方向已经成立的证明箭头。

### 7.2 支持 AND 与 OR，但不要假装图遍历会证明数学

若目标需要多个共同前提，应表示为：

$$
(A\land B\land C)\Longrightarrow G.
$$

若是替代路线，应表示为分别足够的两条候选机制，而不是误写成所有路线都必须完成。

更重要的是，“A 已检查”和“B 已检查”不自动意味着它们能共同使用。需要检查是否处于同一个背景、参数顺序和见证对象之下。

### 7.3 一个最小示例：共同对象不能在压缩中消失

考虑教学性质的关系：

$$
R(t,x)\iff x=t,\qquad t\in[0,1].
$$

对每个 t 都存在满足关系的 x，但不存在对全部 t 都满足关系的同一个 x：

$$
\forall t\,\exists x\ R(t,x)
\quad\not\Longrightarrow\quad
\exists x\,\forall t\ R(t,x).
$$

这是本指南中的独立逻辑示例，不是对任何实际科研项目的结论。

快理解层不能把二者都概括成“存在合适对象”。否则下层每个局部陈述即使成立，骨架仍然可能在最关键的位置错误。

### 7.4 连续性方法的骨架示例

以下只是示意性的任务分解，不主张任何具体方程已满足条件：

$$
\mathcal I=\{t\in[0,1]:\exists u\in\mathcal A_t,\ F_t(u)=0\}.
$$

总览中至少应区分起点、开放性、闭性及允许解空间的边界：

```text
已建立的起点
    + 开放性机制及其真实入口
    + 沿解族的紧性与极限传递
    + 极限仍处于允许的几何范围
    → 目标参数上的存在性
```

“椭圆”不能在总览里自动改写为“线性化可逆”；“有估计”不能自动改写为“足够且一致的紧性”；“每个参数分别有对象”不能自动改写为“同一对象覆盖整条路径”。

一个好的阶段任务是“定位并检查开放性所需的核消失条件”，而不是“研究一下连续性方法”。详细数学做完后，还必须说明骨架里的哪条箭头被支持、被削弱或被推翻。

## 8. checked 与待探索：显示简单，内部语义不能含混

### 8.1 用户界面不需要十几种颜色

常用显示可以保持简洁：

```text
已检查（注明范围与依据）
待探索（注明需要检验什么）
有条件（注明尚未满足的条件）
已发现缺陷（注明被否定的确切主张）
支持已失效／待复核
```

内部至少分开三个维度：**数学依据、项目适用性、版本有效性**。不能用一个布尔值代替全部情况。

```yaml
# 拟议展示数据；由资格服务结合证据生成，而非由作者自由写入。
support_basis: independently_reviewed_argument
applicability: conditional
freshness: current
open_conditions: [example:uniform-constant]
visible_label: "条件推导已检查；项目条件待证"
```

“checked”应解释为“在声明的范围和审查标准下已有支持”，不是“经过形式化内核验证而绝对正确”。来自文献、独立非形式化审查、形式化检查是不同依据，不得混称。

### 8.2 四条必须成立的规则

**规则一：检查过条件命题，不等于检查过其条件成立。**

$$
\text{checked}(A\Rightarrow B)
\quad\not\Longrightarrow\quad
\text{checked}(B).
$$

**规则二：节点有依据，不等于节点之间的连接有依据。** 每个涉及实际数学内容的箭头必须绑定自己的论证或适用性检查。

**规则三：支持失效，不等于结论已被反驳。** 撤回一个 Argument 只能使相应支持失效；要标记反例成立，还需要满足原假设且违反原结论的证据。

**规则四：未找到反例，不等于证明；未确定蕴含关系，不等于互不蕴含。** FDH 的候选比较尤其必须遵守。

### 8.3 接纳并不是自动判真

内核可以自动检查：引用是否存在，版本是否一致，审查是否覆盖精确对象，是否存在显式开放条件，评审输入是否违反隔离规则。

内核通常不能仅凭结构化数据确认一段非形式化推导是否真的有效。因此，高风险新论证仍需适当的独立数学检查；软件通过只能形成“满足接纳契约”的结论。

上层摘要的准确性也需要检查。例如，下层证明的是局部结论，上层不能写成全局结论；下层常数依赖额外数据，上层不能省略该依赖。

### 8.4 失效传播与版本更新

采用“精确依赖驱动”，而非“改过一个文件就把全库重新审查”。

当某条支持撤销或其适用背景改变时，标记依赖它的上层主张及当前路线状态需要重评；不删除原记录，不抹去历史上曾作出的决定。

新增一篇论文的新版，不自动说明旧版中每条定理都错误。旧来源 occurrence 与旧快照应保留。系统应区分固定版本引用和跟随当前版本的引用，并提示有待核对的实质差异。

若新的支持替代旧支持，重新验证受影响的接口即可；不应机械重跑仍然有效、未被污染的全部局部审查。

### 8.5 防止循环自证

研究图可以有探索回流；支持图不能因为 A 引用 B、B 引用 A 就获得闭合资格。

对于需要共同解决的循环子问题，应保留为待解决的联合职责，直到出现独立的共同论证或合法消去循环依赖的机制。图上路径存在不是证明完成。

## 9. MAIN：真正的数学战略角色，而非行政分发器

### 9.1 常态职责

MAIN 要持续理解原问题，发现新的可用模块，比较连接机制，定位最能改变研究选择的未知接口，安排并行或顺序的定向尝试，并把结果更新为新的研究判断。

这需要强数学推理。把复杂证明移给阶段任务，不意味着 MAIN 可以只看标题、票数和完成率。

MAIN 可以做短小的量词检查、维数检查、模型 sanity check 和候选推导草图。把每个显然的核对都拆成新任务同样低效。

但是，MAIN 不应把长时间的主线证明攻坚藏在战略会话中；需要成为正式研究依据的新推导，应形成明确的研究任务或正式候选论证，并按其重要性检查。

### 9.2 默认输入应由“全库倾倒”改为“分层入口”

建议 MAIN 每次获得：

```text
原目标／D0 与当前有效指导
        + 当前研究骨架与核心模块接口
        + 新增／失效的数学事实和失败证据
        + 活跃任务及尚未检查的增量
        + 可按需展开的精确来源与详细论证
        + 当前授权、预算、控制状态
```

这不是允许 MAIN 用模糊摘要代替前提。它可以依赖已经获得相应资格的精确接口；遇到新迁移、版本变化、含糊条件、审查缺口或决定性争议时，必须向下展开。

阶段研究任务则必须实际取得完成其职责所需的完整相关数学材料，不能只收到 MAIN 的两句话描述。

### 9.3 不规定“每轮必须换路线”

MAIN 可以继续有希望的长线，也可以因新证据重启旧路线。评估应基于新增机制、缩小的缺口、被排除的错误假设或更明确的失败原因，而非路线年龄和文件数量。

重复相同失败尝试，需要说明哪些数学输入、方法或诊断发生了变化。仅改任务名字、换表述、重新要求“深入思考”不构成新的研究基础。

### 9.4 事件驱动循环

以下是领域逻辑示意，不是必须照抄的程序：

```text
on relevant_event:
    读取最新控制与授权；已暂停则不新增科研调用
    核对原目标、快照、有效指导与 MAIN 所有权
    区分已接纳成果、候选输出、未知传输状态和未读增量
    更新受影响的模块／transition／路线判断
    提出能改变研究选择的具体问题
    在原范围和授权内选择职责、输入、停止条件与并行关系
    派发，或者等待明确的任务／材料／人工条件
    保存实际决策依据和下次需要判断什么
```

定时器只负责发现状态变化或审计到期，不能在没有事件和需要的情况下反复调用模型“想一想进展”。

## 10. 保留 TRH／FDH，但重写角色责任落点

阶段编号仍表示科研职责，不表示从前到后必须执行一次，也不表示每一个编号都必须单独发出一个 CLI 调用。[R4]

### 10.1 TRH 的快／慢职责对应

| 阶段 | MAIN 主要负责的快理解工作 | 定向任务主要交付的详细工作 |
|---|---|---|
| P1 | 决定哪些背景和入口模块存在歧义 | 精确核对定义、假设、符号、量词与归一化 |
| P2 | 倒推目标所需的候选中间输出 | 证明／反驳具体归约，核对必要与充分方向 |
| P3 | 比较机制、瓶颈与判别尝试 | 对关键可行性判断提供实际数学依据 |
| P4 | 选定可执行问题和成果预期用途 | 首次或重新进行证明、估计、构造和反例尝试 |
| P5 | 判断哪个接口使成果尚不能达到目标 | 检查假设、定义域、常数、量词、共同见证对象 |
| P6 | 决定 AND 分解、OR 路线与模型切片 | 检查分解依据、提升论证和兼容条件 |
| P7 | 选择需要重建的成熟框架和迁移入口 | 读取原始方法，重建机制，验证迁移，不只写摘要 |
| P8 | 聚焦当前最关键、可改变路线判断的问题 | 定向攻坚、修补、反驳、计算与明确失败定位 |
| P9 | 冻结精确审查对象，安排相互独立的职责 | 证明检查与原假设下的反例探索，保持判词隔离 |
| P10 | 组织候选整体骨架与待组装接口 | 实际完成全局拼接，保留不能消去的条件 |
| P11 | 从原目标重新判断到底取得了什么 | 必要时委派核对关键结论或遗漏职责 |
| P12 | 定位整体组装新增的检查范围 | 独立检查全局接口；复用仍然有效的局部审查 |
| P13 | 说明本轮真正的知识变化与下一步选择 | 基于精确证据生成规定的可读轮次报告 |

P4 与 P8 都做真实数学；不能把 P8 限制为改稿。P9 与 P12 的差异不能因增加快理解层而消失。

每次进入 P14 前保存 P13。续轮仍是原 Goal、原目标和原有授权内的控制行为；停止与成功不能混同。

### 10.2 FDH 的快／慢职责对应

| 阶段 | MAIN 的战略责任 | 定向任务的详细责任 |
|---|---|---|
| D1 | 建立现象、机制、边界与失败类型的证据骨架 | 重建案例、来源、失败推导，核对假设 |
| D2 | 提出候选及值得比较的逻辑关系 | 给出精确表述，核对量词和附加条件成本 |
| D3 | 选择最可能改变候选取舍的判别研究 | 具体构造、证明、反例或适用性检查 |
| D4 | 冻结候选集合及比较关系的审查问题 | 独立核对候选、反面证据、遗漏和相互关系 |
| D5 | 综合可选择的候选、局限及未知关系 | 提供足够证据让研究者作真实选择 |

D0 的固定背景与允许调整轴不可由 MAIN 偷换。普通 D5 进展综合不必暂停；正式交付给人选择时暂停。

用户继续探索，恢复同一个 FDH Goal；用户明确采用候选，才建立独立且暂停的 TRH 实例，再获得启动授权。不得把 FDH Goal 原地改成另一个目标。

### 10.3 不把科研范式误称为输入模态

TRH/FDH 是研究模式与职责体系，不是通常意义上文本、图像、音频的“多模态”。开发文档宜使用“多模式科研协议”或“动态科研职责流转”，避免与模型输入模态混淆。

## 11. 阶段任务必须明确，但不能被写成机械脚本

### 11.1 最小 TaskContract

每个任务至少知道：

| 字段 | 内容 |
|---|---|
| question | 一个精确问题；需要证明、反驳、构造或比较什么 |
| scope | 原目标／候选／模型范围，不允许默改 |
| purpose | 为何现在做，它会影响哪个研究选择 |
| input_refs | 必要的精确材料版本及其资格和开放条件 |
| transition_ref | 对应哪一条连接；尚未成图时可以明确为空并说明 |
| acceptable_outcomes | 证明、反例、附加条件、明确失败、未完成等合法结果 |
| stop_or_return_condition | 哪些结果应当回报 MAIN，而不是自行扩张职责 |
| isolation_and_authorization | 可读材料、通信权限、工作区、执行授权 |

任务应有针对性，但允许 worker 在职责内选择具体数学方法。不能要求 MAIN 预先知道完整证明才能派发任务。

### 11.2 双重交付

任务的产物应同时包含详细数学与对快理解的影响：

```yaml
# 拟议结果结构；正文仍以可读 Markdown／数学公式为主。
result:
  scope: example:original-question@v1
  outcome: CONDITIONAL_RESULT
  detailed_records:
    - example:argument-new
    - example:statement-conditional
  fast_layer_delta:
    target: example:transition-compactness@v2
    before: "怀疑现有估计已足够"
    after: "只能得到较弱结论；另需一个明确的一致性条件"
    changed_assumptions: [example:uniformity-condition]
    supports: [example:argument-new]
    decision_consequence: "原闭性箭头仍开放；下一步检查一致性条件"
  remaining_gap: "精确说明尚缺的数学内容"
  failure_or_retry_basis: "再次尝试需要发生什么实质变化"
```

这是一次研究输出的两个视角，不是要求每个任务结束后再调用一个模型写“漂亮报告”。普通 task handoff 应承担这项职责。

### 11.3 失败是知识，但必须分类

至少区分：原命题在原范围内被反例否定；某个加强命题失败；某条归约失败；某种方法失败；假设不足；文献无法取得；数学工作未完成；软件或传输失败。

只有满足原命题全部假设并违反其结论的证据，才可能被接纳为原命题反例。

方法失败的回写应定位不可用的机制／接口，而非只留下“尝试失败”的日志。下次 MAIN 检索这个机制时，应看见失败原因和重新尝试的条件。

### 11.4 与独立审查的关系

快层修改需要检查是否忠实于详细输出，但不必把每次措辞修订升级成一轮新的整体数学复核。

当变更涉及结论强弱、适用范围、关键量词、连接方向、额外假设或整体拼接时，应安排对应范围的数学检查。纯展示改动可使用更轻量的结构与语义一致性检查。

## 12. 观察／讨论会话：安全地了解项目，而不成为第二个 MAIN

### 12.1 默认使用一致快照

新 Codex 会话不应对正在变化的项目目录任意遍历后声称获得了“一致的当前进展”。建议先从内核取得只读观察快照。

快照最少包含：项目与实例、知识提交、控制版本、生成时间、骨架版本、报告版本、快照截止后是否存在已知增量，以及允许读取的证据清单。

同一次回答引用固定快照。需要更新时显式 refresh，并展示有意义的数学变化，而不是把不同时间的资料混成一份未标注的“最新状态”。

快照中可列出在途任务和未接纳输出，但它们不得混入已检查结果。

### 12.2 观察角色的权限

观察任务可以读取许可范围内的骨架、原文和报告，可以在独立 scratch 空间写讨论记录；不能写 canonical 科研记录、控制日志、预算、MAIN 会话绑定或支持状态。

**单独开一个聊天线程，不等于实现了只读隔离。** 仅靠 AGENTS.md 的文字约定、另建 Git worktree 或让模型承诺不改文件，都不足以提供安全边界。

应使用真实的文件系统只读挂载／受限执行环境，或仅暴露经过服务端权限检查的读取工具。观察任务不应继承可写内核目录的 shell、其他 MCP 写接口或高权限凭据。

OpenAI 的 Codex 说明特别提醒：其 shell 沙箱并不自动替所有 MCP 工具实施同样的防护；PMRS 工具必须自己校验权限。[E1]

### 12.3 讨论默认是讨论，不是执行授权

将输入意图区分为：

```text
QUESTION          询问或请求解释
IDEA_PROPOSAL    供考虑的研究想法
GUIDANCE         用户明确要求施加的方向性指导
CONTROL          暂停、继续、结束等控制
AUTHORIZATION    启动、追加预算、范围变更等授权
```

这是一种建议的协议划分，不要求实现时沿用这五个字符串。

模型自己形成的想法必须保留“模型提案”的来源，不能通过一句“用户似乎希望”获得 HUMAN 权限。

用户说“把这个想法发给 MAIN 参考”，可以在原范围内提交建议；用户说“按这条路线优先研究”，则应保留具体原文并记录有效指导。两者都不自动授权改变原目标或追加预算。

### 12.4 推荐的操作体验

```text
用户：打开项目 A，解释当前真正取得了什么，不要改变研究状态。
观察会话：读取快照，展示数学骨架、证据、未决接口和在途任务。

用户：我们讨论一下，能否把这个估计换成另一种控制量？
观察会话：讨论，形成带条件与风险的想法，不直接派研究任务。

用户：把它作为建议发给 MAIN，保持原范围和原预算。
观察会话：提交带来源、快照与边界的提案，返回收件记录。

MAIN：在可用的安全边界读取提案，决定采用、部分采用、拒绝或待验证。
系统：保存实际采用范围、理由和后续任务关系。
```

对于已暂停实例，提案可以入箱，但入箱不恢复 Goal。用户仍需给出明确继续授权。

### 12.5 不夸大送达

提案应区分：已保存、已送达、已读取、已考虑、已采用、被替代。不能在只写入文件后就回答“MAIN 已经按此调整”。

已有 `assistant.py` 和指导机制可以作为起点；需要补充独立 Codex 入口和真实权限边界，不能把现有项目助手的存在误当作所有隔离要求都已完成。[R7][R3]

## 13. 并发、恢复与权限：保留少量但坚固的机制

### 13.1 每实例唯一控制者

每个 TRH/FDH 实例有一个逻辑 MAIN，控制权绑定当前会话、授权和所有权代次。多实例可以各有 MAIN；“唯一”不是整个工作区只允许一个项目研究。

所有科研派工都必须通过内核检查当前控制版本。旧会话、迟到事件、重复任务结果和已失效的控制者不能重新获得派工权。

可以使用租约与 fencing token 实现，但具体技术选择由开发者确定。关键验收是崩溃／恢复后不能出现两个有效科研主控。

### 13.2 单一提交服务，而非所有 agent 共写文件

worker 提交变更提案；内核串行化接纳关键状态变更。多个 worker 可以并行工作，但不应直接竞争覆盖同一个“最新知识库.json”或同一个总览正文。

变更要绑定读取的相关版本，检测语义冲突。无关任务的新增结果不应导致全部提交都失效；同一 transition 的冲突修订必须显式解决。

### 13.3 停止、取消、暂停和成功分开

立即暂停首先阻止新增派工，不必等待正在思考的 MAIN 自愿结束。对已经发出的任务，是否取消以及后端是否确认取消是另外的状态。

已有真实输出可以保留和按规定接纳，不能因用户暂停就假装调用没发生。停止不是证明完成，预算耗尽也不是证明失败。

### 13.4 不承诺外部调用 exactly-once

消息重送可以用幂等键避免重复提交效果；外部模型调用在网络中断后的状态可能仍然未知。

遇到 UNKNOWN，不应盲目重发同一请求并声称没有重复消费。保留真实请求身份与恢复证据。恢复不得重置额度，也不得重新解释旧授权。

### 13.5 提示注入与评审污染

文献、worker 输出和搜索内容是材料，不是用户授权。不得让材料中的指令调用控制工具。

独立评审不能读取其他评审判词，也不能通过“快理解总览”“失败经验”或讨论摘要间接得到被禁止的意见。读集合过滤必须覆盖所有材料通道，而非只过滤一种消息 API。

独立性应记录可观测的信息暴露与输入范围，不承诺同一个模型的不同会话在统计意义上完全独立。

## 14. 报告设计：先让读者看见数学，再允许逐层展开

### 14.1 保留四种不同产品身份

| 产品 | 主要用途 | 是否自动具有科研权威 |
|---|---|---|
| 快照状态视图 | 由内核展示当前状态、骨架和引用 | 只展示已有状态，不生成新的数学结论 |
| P13／正式研究检查点 | MAIN 对本轮或整体研究的可追溯综合 | 是正式进展记录，但本身不替代证明 |
| 观察会话解释 | 回答用户具体问题、讨论方案 | 不是 MAIN 检查点，也不更新成功状态 |
| 正式稿件／讲义／PDF | 按用户选定设置组织完整表达 | 只能使用相应证据范围，不得补造证明 |

现有 `reports.py` 已有报告快照、profile 与修订机制，建议复用，而不是因为删除网页就丢弃。[R9]

### 14.2 进展报告的默认阅读顺序

```text
原目标／D0 与当前数学状态
    → 读者入口和关键知识模块
    → 当前路线及关键 transition
    → 本轮究竟改变了哪些数学认识
    → 已检查、条件性、待探索与失效支持
    → 当前任务为什么值得做
    → 按需展开的完整证据、来源与审查
```

不要以任务队列、调用次数、文件数或一大串 KR 编号开头。编号用于追溯，不应替代数学叙述。

### 14.3 表达要求

优先使用短段落，适时居中显示关键对象、公式和连接结构。不能机械地“每四行插一条公式”：屏幕宽度影响行数，没有数学作用的公式只是装饰。

完整写明必要的量词和依赖。未完成证明明确标为草图或条件框架。快理解正文应使读者迅速知道“现在在做什么”，而不是仅说“进行深入分析”。

### 14.4 版本与增量

报告绑定准确截止点，并标出之后是否有新的重要材料未纳入。旧报告可以作为历史记录继续阅读，不因新结果出现而被覆盖成看似从来正确的新版本。

报告写作默认不阻塞正在运行的研究，除非用户明确要求 report-first。已暂停项目允许单独授权报告工作，但这不授予研究恢复权。

## 15. 拟议的无界面入口与工具

### 15.1 已有 CLI 与新增接口分开说明

4.2.2 已有 `knowledge current/frontier/diff/sources`，以及 `status`、`start`、`pause`、`resume`、`report`、`p14-control` 等命令。[R10]

以下是拟议的新用户体验，名称尚可调整，**不能当作现有命令执行**：

```sh
pmrs observe PROJECT --instance INSTANCE --snapshot latest
pmrs kb map PROJECT --instance INSTANCE
pmrs kb explain PROJECT --module MODULE --depth interface
pmrs kb expand PROJECT --ref EXACT_REF
pmrs proposal submit PROJECT --instance INSTANCE --file idea.md
pmrs guidance submit PROJECT --instance INSTANCE --file guidance.md
pmrs report progress PROJECT --instance INSTANCE --snapshot SNAPSHOT
```

这些入口可以通过 CLI 或本地 MCP／RPC 工具供 Codex 使用。取消 Web UI 后，不要求保留一个隐藏的浏览器服务作为所有操作的唯一入口。

### 15.2 工具角色分组

| 角色 | 工具范围 |
|---|---|
| Observer | snapshot、map、module、exact evidence、report、read-only diff |
| Advisor | Observer 工具，加独立提案提交；操作性指导需对应真实授权 |
| MAIN | 许可范围知识读取、派工、任务通信、路线修订提案、等待与正式进展提交 |
| Worker | 冻结／明确许可的材料读取、自己的 scratch、任务结果提交 |
| Reviewer | 隔离材料读取、自己的检查结果提交 |
| Human control | 启动、暂停、继续、结束、预算和范围决策 |

权限是由调用者身份和服务端检查授予的，不由模型在工具参数中写一个 `role: human` 获得。

### 15.3 默认安全行为

进入项目、阅读文件、请求解释或打开报告均不自动启动科研。新会话不自动附着为已有 MAIN 的可写控制者。

需要 MAIN 身份的会话必须通过明确的启动／恢复入口绑定实例。开发程序的 Codex 会话与运行科研的 MAIN 会话也应分开，避免软件维修会话误改活跃科研状态。

## 16. Codex 与 DeepSeek Harness：可以替换底座，不可替换数学契约

### 16.1 不依赖 ChatGPT Desktop 是可行目标

Codex 官方提供 CLI 非交互执行和 App Server 接口，允许程序化组织任务与会话；使用这些接口不要求把 ChatGPT Desktop 作为 PMRS 的程序基础。[E3][E4]

需要分别回答三个问题：使用哪一个交互客户端，使用哪一个 agent runtime，调用哪一个模型。它们不是同一个选择。

开发代码也可以在普通代码仓库、终端和 Codex CLI 中完成。“不使用 ChatGPT Desktop 开发”与“把运行时从 Codex 换成其他 harness”是两个独立决定。

### 16.2 DeepSeek Harness 确实是可选底座

DeepSeek 官方将 `dsh` 定位为开源 agent harness。其公开架构采用 Cordis 插件组成，可替换模型适配器、工具、会话日志和 agent loop；配置包含 `headless`、`sdk` 等不依赖 Web UI 的 profile。[E5][D1][D2]

因此，从软件组成上，可以把 PMRS 的领域知识服务、角色协议、指导收件箱、派工和接纳接口做成 DSH 插件或 SDK 集成。

这不要求使用 DeepSeek 模型，也不说明原先 Codex 的模型访问权限、认证、服务强度或计费安排可以原样迁移。后端能力和用户授权必须分别确认。

### 16.3 一个会影响本项目的具体限制

DSH 当前子 agent 文档区分本地可继续会话与外部执行。外部 Codex、Claude Code 等后端提供一个执行 handle；外部执行不接受后续消息。本地可继续子会话才具备相应收件和恢复机制。[D3]

所以，“DSH 已有 Codex 子任务”不等于“MAIN 可以像现在一样在任务运行中定向通信”。

若 PMRS 依赖持续通信，有三种可评估方式：保留 PMRS 自己的 Codex 任务适配器和消息服务；开发能满足所需契约的继续执行桥接；或者选择经过验证的本地可继续执行后端。

不能默默把持续通信降成一次性 prompt，并宣称完全等价。

### 16.4 现有定制 Codex 原生运行时也不能直接假定可替换

4.2.2 的公开文档说明 MAIN 依赖定制 app-server、配套原生程序和绑定授权的 root-turn 准入机制。[R2][R3]

新版可以争取减少对定制构建的依赖，但必须先证明替代接口能保持暂停、有限授权、持久 Goal、恢复和实际观测语义。仅仅能调用 stock Codex App Server，不构成等价迁移。

App Server 有 `turn/steer` 等能力；调用时应使用其实际要求的活动 turn 身份，不应把一个本地“发送成功”当作当前 MAIN 已读取或采用。[E4]

### 16.5 推荐路线

**优先选择：领域内核独立，Codex-first，无自建 UI。**

先把用户最需要的快理解层和安全观察会话做出来，同时保留当前关键执行语义。然后单独实现 DSH 适配器，在相同领域契约下验收。

不建议同时重写知识库、切换 MAIN 模型、切换运行时、废弃全部控制协议，再用一次科研实验判断整体好坏。那样失败时无法知道问题出在哪里。

DSH 官方目前明确标注 developer preview 和可能出现破坏性变更，应固定实际依赖版本及能力清单。[D1]

### 16.6 后端最小能力清单

| 能力 | PMRS 所需保证 |
|---|---|
| start / resume | 绑定明确逻辑实例与实际会话身份，恢复不创建另一科研主控 |
| event stream | 区分输出增量、调用结束、任务失败与捕获完成 |
| task isolation | 实际限制文件、工具与消息暴露，不能只靠角色提示 |
| steer / inbox | 说明是否支持运行中指导；不支持时明确阻塞或使用已验证替代机制 |
| cancel / pause | 区分禁止新调用、已发任务取消请求和后端确认 |
| capture | 保留原始输出与失败；结构化输出无效不能改造成虚构科学结果 |
| usage | 保存可观测用量，未知保持未知，父子重叠不盲目相加 |
| recovery | 未知请求不盲目重发，授权不重复消费或重置 |
| tools | 服务端身份与范围验证，阅读与控制权限分离 |
| versioning | 固定版本，记录实际支持能力与已执行的集成测试 |

这份表是待验证的 PMRS 需求，不是宣称任一后端已经全部满足。

## 17. 存储与目录：人能阅读，机器能可靠提交

### 17.1 原则

保持“正文可读、身份精确、提交受控”。不要为了结构化而让 agent 手工维护大量重复 JSON；也不要让所有事实只存在于无法追溯来源的一篇 Markdown 总结里。

可读正文存一次，元数据引用正文身份。索引和视图应能重建，但作者提出的数学骨架、选择理由及未证连接不应被当作无价值缓存随意丢弃。

### 17.2 拟议逻辑布局

下列是职责布局示意，不声称为 4.2.2 当前真实目录结构，也不要求盲目搬动已有 `records/` 与 blob 数据：

```text
project/
  原有 records/ 与正文／来源存储       # 保留精确证据与身份
  blueprints/                       # 版本化知识模块、transition、研究骨架
  reader-profiles/                   # 解释基线；不授予数学资格
  refinements/                      # 上下层精确对应，可复用既有支持结构
  proposals/                        # 讨论提案与来源
  reports/                          # 快照报告与正式报告
  views/                            # 可重建的当前总览、导航、检索索引
  runtime/                          # 控制、会话关联、任务和恢复资料
  scratch/                          # 隔离的各任务工作区，非正式证据
```

实际权限不由目录名决定。canonical 内容只能经接纳／提交服务更新；只读导出可以放在观察者的独立目录。

### 17.3 避免两份“最新真相”

`blueprints/` 的作者版本与 `views/` 的可读当前投影要有明确来源关系。编辑一个导出的 `overview.md` 不应立即改写 canonical 路线或结论。

若允许用户编辑 Markdown 提交想法，程序应把修改识别为提案，并显示语义差异。涉及新的数学内容时，仍需落实到相应证据或待探索状态。

### 17.4 检索先改入口，不必先上复杂向量库

第一版优先索引模块标题、用途、输入、输出、机制、适用边界、失败条件及 transition 关系，并支持完整正文检索。

可以以后增加向量检索，但检索相似不能授予适用性或证明资格。搜索结果应显示覆盖边界；索引上限或未索引部分不能被隐藏。

查询“什么能提供所需的一致性”应能找到模块接口和失败记忆，而不只是命中正文前 2048 字节中恰巧出现的同一个词。

| `native_main.py`／原生适配相关组件 | 分离后端接口，先保持既有语义 | 对持久 Goal、准入与恢复做能力对照，不盲换 stock runtime。 |
| `desktop.py`、桌面浏览器启动与 UI 分支 | 在功能迁出后移除 | 不留下必须启动网页才能使用的隐性依赖。 |
| Web 展示资产与展示专用路由 | 移除 | 先提取被其调用的应用服务；保留必要证据读取能力的非网页入口。 |
| 新增快层模块 | 轻量新增 | blueprint、refinement、reader profile、fast delta 与语义一致性检查。 |
| 新增后端适配层 | 分阶段新增 | Codex 与 DSH 的能力差异显式化。 |

### 18.1 第一版不要新增不必要的基础设施

不必先引入新图数据库、分布式任务平台或另一套全文档同步系统。优先复用已有 Store、事件、支持和报告能力，让新增语义可用、可检查。

当性能测量表明现有存储成为瓶颈时，再选择对应基础设施。不要把“图结构的研究思想”误解成“必须先部署图数据库”。

## 19. 变更接纳流程

### 19.1 增量提交

建议一个知识变更提案能够同时携带：详细新记录、快层修改、精确落实关系、失效影响、任务交付说明。

核心顺序如下：

```text
保存原始任务输出
    → 验证格式与实际输入身份
    → 验证范围、引用、开放条件和独立性要求
    → 接纳为具有明确资格的候选／证据
    → 核对快层表达没有放大详细结论
    → 原子提交相关版本与依赖变化
    → 更新可重建视图与必要的 MAIN 增量
```

不能在下层尚未接纳时先把上层路线标为成功。允许暂存待接纳的快层草稿，但其身份必须明确。

### 19.2 控制状态变化时的处理

提案提交前后可能出现用户暂停、预算耗尽或目标控制版本变化。

已经发生的数学输出仍可按规则保存；这不意味着允许后续派工。结果接纳权限、MAIN 科研选择和新增调用授权必须分别检查。

### 19.3 低成本反重复

在派发前比较任务的精确目的、相关数学输入、目标接口、失败机制和新增研究依据。

相同问题、相同有效输入、相同方法与相同障碍的再次派工，应提示缺少新的研究理由。不同的独立审查职责、反例探索与证明检查，不能因目标相同而被错误去重。

记录的是可解释的重复基础，不建议使用不可解释的单一“相似度阈值”自动封死一条科研路线。

## 20. 迁移方案：保留已有研究，不偷换知识资格

### 20.1 不自动改旧项目

4.2.2 文档本身不承诺旧项目格式迁移。[R2] 新版应有明确的 schema 版本与离线迁移入口。

建议在用户明确选择后，把旧项目导入新目录，保留原项目不变。迁移结束保持暂停，给出迁移报告，再由用户决定是否恢复研究。

### 20.2 迁移顺序

| 步骤 | 要求 |
|---|---|
| M1 原件保全 | 保存原始记录、来源、支持、审查、输入输出与控制历史的精确身份。 |
| M2 语义盘点 | 标出原目标、已知有效支持、条件性结论、失效支持、路线与待决任务。 |
| M3 生成骨架草案 | 可以由模型在单独授权下组织快理解，但默认是草案，不直接升级为 checked。 |
| M4 建立落实关系 | 把每个重要模块和箭头绑定回原证据，并检查压缩是否保留关键条件。 |
| M5 范围化检查 | 对真实变化和新的全局组织关系检查，不重做所有已有效的局部证明。 |
| M6 交付与暂停 | 提供未映射内容、不能复用的资格和剩余工作；不自动启动研究。 |

没有付费授权时，迁移工具可以完成确定性文件与元数据转换，但不能擅自调用模型构造新骨架。

### 20.3 不能从运行状态推导数学状态

`completed` 的任务不等于已证明的 Statement；曾经发布报告不等于其中每条连接都获得独立支持；旧总览里一句“只差最后一步”不等于其他所有条件已经解决。

原有合法且版本可追溯的支持可以复用，但新的快层表达必须证明自己忠实于那些支持的范围。

### 20.4 MAIN 身份与后端更换

第一阶段尽量保留现有 MAIN 绑定与执行语义。跨后端迁移需要显式终止或冻结旧控制权，再建立新的执行绑定并保留继承来源。

不能只复制一个 session ID 或改配置文件，就宣称是同一个已经验证过的原生 Goal。逻辑科研身份与后端线程身份要分别记录。

## 21. 开发里程碑与交付物

### 阶段 A：先冻结正确边界

交付产品定位、角色权限、原目标／授权边界、快慢层契约、状态语义与后端接口的简短架构决策记录。

此阶段不改变实际科研实例，不删除旧证据，不运行新研究。

### 阶段 B：先实现“安全读懂项目”

提供无界面的只读快照、证据展开、报告读取和观察角色入口，复用现有 CLI、assistant 与报告服务。

让新 Codex 会话能够解释原目标、已有成果和未决问题，同时通过测试证明它不能写入或启动研究。这是最早能验证用户体验的交付。

### 阶段 C：把快理解变成第一类研究状态

实现知识模块、transition、骨架、ReaderProfile 与上下层落实关系，先用少量明确教学材料测试。

重要交付不是生成了多少卡片，而是错误的量词、条件和接口会被揭示，读者能清楚找到下一项可检验工作。

### 阶段 D：完成 MAIN—任务—知识回写闭环

改写 MAIN 与 worker 的实际输入契约，接纳双重结果，更新受影响的骨架，让下一次派工引用新的数学依据。

通过可控场景测试机制选择、失败吸收、重试理由、范围变化和独立审查隔离。

### 阶段 E：移除自建 Web UI

在所有必要用户操作都有无界面入口后，移除网页资产、浏览器启动和展示专用路由。

验证查看、讨论、指导、暂停、恢复、FDH 选择、报告和维护均不依赖浏览器。不是只把网页隐藏起来。

### 阶段 F：后端互换验证

先验收 Codex 适配；再以相同领域场景验收 DSH 适配，特别检查后续通信、恢复与权限差异。

框架更换不构成研究成果，也不构成数学正确性保证。

### 阶段 G：受控真实科研评估

仅在用户明确批准项目、范围、模型与预算后运行。保留全部失败和未执行项目，不把教学 fixture 或离线单元测试冒充真实研究验收。

可以先做一个固定目标 TRH 和一个明确 D0 的 FDH 小规模场景，再决定是否迁移长期开放问题。

## 22. 验收矩阵

下表全部是**建议执行的测试**，没有在本次咨询中执行。“应通过”描述预期，不是实际测试结果。

### 22.1 快理解与数学语义

| ID | 场景 | 预期行为 |
|---|---|---|
| K01 | 模块只有定理名字，没有输入／输出 | 标记入口信息不足，不能冒充可调用机制。 |
| K02 | 有精确来源定理，但本项目适用性未检查 | 区分模块依据与项目适用性，后者保持待探索。 |
| K03 | 下层是条件结论，上层省掉条件 | 拒绝该资格升级或要求修订；不能显示无条件 checked。 |
| K04 | 下层是逐参数存在，上层写成共同对象存在 | 捕获量词／见证变化，保留开放 transition。 |
| K05 | 多个节点 checked，连接未证明 | 路线保持开放。 |
| K06 | AND 路线漏掉一个必要职责 | 总览与报告显示未完成条件，不宣称只剩已列的一步。 |
| K07 | OR 路线中一个候选失败 | 只影响相应路线，不错误要求全部路线都完成。 |
| K08 | 反向搜索把必要条件当充分条件 | 标出方向错误，不形成证明闭合。 |
| K09 | 一个 Argument 被撤销 | 下游支持待复核，而非自动判定结论为假。 |
| K10 | 同一来源出现新版 | 保留旧版本；提示适用性变化，不无依据整体清空支持。 |
| K11 | A、B 互相引用但无外部支持 | 不允许通过循环引用获得 checked。 |
| K12 | 任务只输出详细论证，没有说明骨架变化 | 交付标记不完整，可补回写，但原始数学输出仍保留。 |
| K13 | 任务方法失败 | 更新机制失败记忆，不把原命题标为被反驳。 |
| K14 | 新增 reader profile | 只改变解释入口，不改变数学资格。 |
| K15 | 查询内容位于正文前缀之外 | 搜索说明覆盖；完整检索或模块索引可以实际定位。 |
| K16 | 新路线写入 `research_routes` | 通用搜索与 MAIN 快层入口能访问授权范围内的路线。 |

### 22.2 角色、控制与恢复

| ID | 场景 | 预期行为 |
|---|---|---|
| C01 | 观察任务尝试覆盖知识正文 | 被真实权限边界阻止，不仅靠模型自律。 |
| C02 | 观察任务尝试调用隐藏的写工具／shell | 所有路径都不能绕过只读权限。 |
| C03 | 打开已暂停项目并请求解释 | 保持暂停，不触发研究调用。 |
| C04 | 讨论形成想法但未要求提交 | 不发送操作性指导，不派研究任务。 |
| C05 | 模型提案伪装 HUMAN 指令 | 拒绝权限升级，保留正确来源身份。 |
| C06 | 用户提交建议给已暂停 MAIN | 可以入箱，但不恢复 Goal。 |
| C07 | 重送相同指导事件 | 幂等保存／应用，不重复追加预算或派工。 |
| C08 | 旧 MAIN 恢复后尝试派工 | 过期控制代次被拒绝。 |
| C09 | 暂停与派工同时发生 | 最新控制边界阻止未获准的新派工，保留已发请求。 |
| C10 | 收到已完成任务的迟到输出 | 按原始身份处理，不重写其已读输入。 |
| C11 | 网络中断后请求状态未知 | 保留 UNKNOWN，不盲目重发并声称零额外消费。 |
| C12 | 崩溃后恢复 | 不存在两个有效 MAIN；范围、预算和暂停不丢失。 |
| C13 | 新增无关科研记录 | 不无理由使所有未提交结果失效。 |
| C14 | 两个任务修改同一 transition | 检测相关版本冲突，保留各自结果并显式合并。 |
| C15 | 独立评审请求读取快层历史判词 | 被权限过滤，或记录暴露并取消所需独立资格。 |
| C16 | 输入文献中含“请恢复 Goal”等指令 | 当作不可信材料，不获得控制权限。 |

### 22.3 协议、报告与后端

| ID | 场景 | 预期行为 |
|---|---|---|
| P01 | TRH 不按编号顺序研究 | 合法职责有依据即可，不机械强制每阶段一次。 |
| P02 | P14 准备续轮但缺 P13 | 不绕过规定报告与控制边界。 |
| P03 | FDH 普通 D5 进展综合 | 不自动进入正式人工选择暂停。 |
| P04 | FDH 正式交付 | 暂停并保留候选、证据、未知比较与选择项。 |
| P05 | FDH 采用候选 | 精确用户选择绑定独立暂停 TRH，不自动启动。 |
| P06 | 候选关系不明 | 不显示为互不蕴含。 |
| P07 | 观察者生成解释 | 不覆盖正式 MAIN 检查点，不改变数学成功状态。 |
| P08 | 报告生成后出现新成果 | 报告保留快照身份，并显示其截止点与增量边界。 |
| P09 | 删除所有 Web UI 入口 | 核心研究、阅读、指导、控制和报告流程仍完整可用。 |
| P10 | 后端不支持运行中通信 | 明确报能力不足或使用经过验证的替代，不静默降级。 |
| P11 | 后端返回结构化完成结果 | 只标执行状态，不直接授予数学支持。 |
| P12 | 后端未报告内部调用用量 | 显示未知，不记为零，也不与父级重叠计数。 |
| P13 | 新版启动旧格式项目 | 要求显式迁移，不隐式修改或启动旧项目。 |
| P14 | 离线迁移缺少模型授权 | 只做获准的确定性转换，不自行付费构建骨架。 |

### 22.4 真正检验“快理解”的行为验收

给观察者或 MAIN 一个没有见过的项目快照，要求它重建研究框架，并提出下一项具有判别性的具体尝试。

应检查它是否保留原目标、正确调用知识接口、区分待探索与已支持内容、识别共同对象与参数问题，以及说明不同结果会如何改变路线。

这类测试应由能够检查对应数学的研究者评估。不能仅由另一个模型给“总体很好”的评价完成验收。

## 23. 怎样判断新版真的提高科研效率

### 23.1 先做可比较的实验

比较两组系统：保持相同模型配置、研究材料、预算、原目标与可用工具，一组使用现有记录加战略记忆，另一组使用新增快理解层和双重回写。

记录真实输入输出。条件允许时使用多个任务、多个运行，避免凭一次成功或失败下结论。

### 23.2 重点评价什么

| 评价维度 | 值得观察的行为 |
|---|---|
| 定位效率 | 找到相关机制和决定性原文需要多少无关读取与调用。 |
| 问题质量 | 下一任务是否精确对应核心障碍，而非泛泛要求研究。 |
| 认识增量 | 产生了新论证、可复用机制、清晰反例或有价值的失败诊断。 |
| 语义可靠性 | 是否保留假设、量词、常数依赖和共同见证对象。 |
| 负面知识利用 | 是否避免在没有新依据时重复同一种失败。 |
| 人类可理解性 | 目标背景读者能否重建路线、找到缺口并参与讨论。 |
| 控制可靠性 | 讨论、阅读、暂停、授权和后端故障是否保持正确边界。 |

调用减少不总是进步：必要的额外验证可能更有价值。新文件更多也不等于研究更深入。

### 23.3 不设置虚假的目标完成百分比

对开放数学问题，若没有合理、可验证的任务分解，不要显示“已证明 80%”。

可以说明某条精确箭头已获支持、某个共同障碍被定位、某个候选被排除、某项全局接口仍然开放。这些是实际可解释的进展。

> 保留原生证据、独立 MAIN、动态 TRH／FDH、授权与暂停、实际输入输出、审查隔离和报告服务。完全移除 PMRS 自建 Web UI，但在移除前提供所有必要功能的无界面入口。
>
> 核心升级是第一类数学快理解层：可调用知识模块、精确 transition、研究骨架、探索前沿及其与详细证据的落实关系。不能只增加一篇 summary，也不能让快层自行授予证明资格。
>
> MAIN 主要负责数学战略探索与有依据的派工。定向任务负责具体数学，并同时交付详细结果与快层变化。允许 MAIN 做必要的短小核对，但不要把长线攻坚隐藏在一个持续膨胀的主控会话中。
>
> 新 Codex 会话默认只读观察／讨论，读取一致快照。其想法通过带来源和版本的提案进入 MAIN；用户授权、科研判断和模型建议分开。不要用提示词代替真实权限隔离。
>
> 先验证 Codex-first 无界面运行；后端接口保持可替换。DeepSeek Harness 可作为第二适配器，但必须实际检查持续通信、恢复、沙箱、用量与权限能力，不能把一次性外部子任务视为完整等价替代。
>
> 先交付离线测试与明确的未测清单。任何真实科研运行、付费验收、旧项目迁移、模型变更或预算增加，都必须使用相应明确授权。报告中严格区分设计要求、静态实现、实际测试和数学结论。

## 25. 第一版完成的定义

第一版应当使研究者可以在一个新 Codex 会话中，安全地读懂某个项目的数学骨架、展开其详细依据、讨论想法并有控制地传递给 MAIN。

与此同时，MAIN 必须能依据骨架选择定向问题，接收详细成果与骨架修订，更新下一步选择；未经验证的连接、条件和失效支持应持续可见。

所有这些必须不依赖 PMRS 自建网页，并且不牺牲原目标、授权、暂停、独立审查和证据追踪。

**只有这条实际闭环成立，才说明“快理解驱动的 PMRS”被实现了。安装了一个新 harness、增加几个目录或写了一篇流畅的 overview，都不足以达到这个定义。**
