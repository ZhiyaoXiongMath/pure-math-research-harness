# PMRS 4.2.0 architecture

This document describes Version 4.2.0. It incorporates repaired scientific responsibilities and execution paths, plus the new project-assistant and exact-report-revision service. Published v4.1.0 remains a distinct historical baseline. See [implementation notes](IMPLEMENTATION-NOTES-4.2.0.md) for the development evidence and its reuse boundaries.

The application exposes one native mathematical research runtime through shared Engine and Workspace services. The browser and CLI share service semantics for TRW, TFDW and SURVEY; neither is an independent research authority.

## Knowledge and evidence

Strict mathematical records retain Context, Statement, Argument, Example, SourceEvidence and Assessment responsibilities. Content identities, logical revisions, production events, consumer-specific qualification, immutable source/body locators, scoped support, independent assessments and withdrawal remain distinct. Preflight, live execution and original-capture recovery use the same scientific admission validation. Saving a statement or citing a publication does not qualify a proof.

SURVEY stores versioned scope, retrieval, reading, coverage, readiness and output-plan metadata alongside native knowledge. Sources, extracted text and mathematical records are separate artifacts. A PDF's original hash is its actual byte hash, not an extracted-text hash. Metadata or abstract access never becomes a full-text reading claim. Readiness binds the selected revisions, dependency closure, evidence and proof commitment; unrelated knowledge changes do not invalidate the selection.

## Execution and retrieval

Each workflow instance owns its target or scope, state, authorization and budget. Stage/role/purpose policies freeze settings before dispatch and refuse unsupported capabilities. TRW/TFDW research and report policies are retained. Survey planning, reading, organization and coverage use registered xhigh roles; substantive reconstruction and independent mathematical checking use max roles. Report and visual roles retain the existing report policies. Product task settings are independent of the development agent's settings.

All 29 stages have explicit scientific input, role and result duties. A bounded work plan declares task-specific selections, exact branch identities and dependencies under one mission; it does not impose a complete stage pipeline. P7 permits N framework-learning and M independent direct-analysis branches. Synthesis consumes the actual accepted accounts of every selected branch, or an explicit reason for deferring optional work; a required unfinished branch still blocks it. P8 supports first attempts as well as repairs, and P11 receives the global gap inventory. Survey reading, organization and review use one finite authorization. Branch labels and new missions cannot reset the same duty's accumulated attempt budget. Existing immutable stage declarations and frozen packets retain their identities.

Ordinary `start_round` delegates to the native automatic-continuation service when no explicit stage or work-plan items are supplied. For TRW, it checks P1–P3 prerequisite work against the selected inputs and applicable accepted evidence, reuses valid results, and assigns missing responsibilities. Later duties follow actual accepted work accounts, concrete gaps and dependencies within the same mission; a stage number alone is not a reason to run a task. TFDW stops at a candidate frontier for human selection. Survey advances selected source reading, organization and independent readiness work; missing sources or knowledge remain visible input requirements, without implicit host retrieval. Explicit finite plans remain a separate supported entry.

The host round account provides deterministic P13-style delivery without a management model call: produced records, failures, unfinished and unperformed responsibilities, and open gaps. It distinguishes dependency and resource waits, authorization exhaustion, execution faults and readiness for a human decision. This projection neither grants mathematical qualification nor requests a manuscript. Formal reports remain explicit operations, and the human retains the P14 continuation, end and handoff decisions.

The live execution queue supports up to eight explicitly authorized calls per project within a shared ten-call host pool. Existing lower project concurrency persists when no override is supplied. Task completion can admit newly ready work while other calls remain in flight. Preparation and physical-resource admission use separate leases and do not consume all model-call slots for the lifetime of a request.

Controlled literature access separates model planning from host retrieval. The host executes bounded queries and downloads, retains provider records, actual URLs and versioned materials, and records explicit failures and access limits. Reading and synthesis consume frozen inputs. Retrieval does not globally enable network or filesystem permissions in mathematical tasks. External text remains source content rather than executable instructions.

Captured results retain original request identity. UNKNOWN is not automatically resent or refunded. Pause prevents new dispatch while retaining in-flight work and captures. Reentry requires changed inputs, a specific issue or explicitly bounded retry grounds.

A correction operation atomically pauses new dispatch and binds the affected responsibility, concrete issue and success criterion to the original mission. Affected unsent work is held; sent requests and captured responses keep their identity. Continuation first recovers eligible original captures and then schedules the concrete correction under the remaining authorization. The explicit human `EXTEND_MISSION_BUDGET` operation adds a finite call amount with a reason, preserving mission, scope, concurrency, frozen requests and cumulative responsibility-attempt limits; it does not start execution. A separate continuation is required. Starting a new mission cannot dispatch the previous mission's unsent prepared requests, and cannot erase its sent-request or capture evidence.

The matching source ZIP includes portable regressions in `tests/test_autoflow.py` (ordinary-start continuation), `tests/test_round_intervention.py` (delivery, correction and finite authorization), and `tests/test_runner_pause.py` (pause/original requests). Tests are source-archive files, not installer payloads. These references identify implementation checks; their executed source identities and bounded reuse for 4.2.0 are recorded separately in the validation report.

## Services and persistence

The native journal uses content-addressed blobs, sparse deltas and reference checkpoints. SQL remains a disposable projection. Ordinary reads do not repair, dispatch or resume work. Product and storage version identifiers are separate. Native backup validates the journal and blobs into a new paused destination; unsupported shapes fail explicitly. Earlier-version migration readers, compatibility adapters and archived research examples remain outside the product.

Preparation counts actual local blob sizes and bounded metadata before large reads. Input, serialized-byte, model-token and temporary-space budgets remain distinct. Task files and offline renderer resources use bounded streaming copies with independent files, never writable links to authoritative blobs. Shared process-identity leases account for physical memory across projects and temporary disk by filesystem. Short preparation has at most two slots, subject to the lower project limit. Phase estimates and recovery boundaries are detailed below; these are application admission budgets, not operating-system memory restrictions or a guarantee against every possible OOM.

Only reconstructable caches are reclaimed. Native checkpoints retain at most four files within 128 MiB. A checkpoint-producing commit preflights its complete state against the 48 MiB serialization limit; exceeding that supported boundary blocks publication before HEAD advances. This is not a source-library size limit or an unlimited-history guarantee. A missing old checkpoint is replayed from immutable deltas. Settled, sealed task input copies may be removed while original packets, captures and receipts remain. Active and UNKNOWN work is protected. Read-only caches have bounded capacity and exact revision/stat keys; actual admission and delivery still verify integrity. ENOSPC and interrupted atomic publication preserve the prior valid state or a complete published state, never a successful half-file. An already captured result remains recoverable under its original identity after the blocking storage or state-size condition is resolved.

Each desktop workspace has a loopback service, session/origin/CSRF protection, stable workspace identity and durable operation receipts. A retry recovers the original operation; a deliberate new operation receives a new key. Workspace receipts recover completed work after service restart and port changes without resending a model request. The 4.x workspace/configuration path retains its `4.0` name while application installations and menu entries use the full product version.

## Reports and interface

TRW/TFDW retain paired lecture/minimal reports. Survey Knowledge only has no manuscript requirement; an explicit Survey writing plan requests only its selected minimal, thematic or lecture profile. Writing consumes frozen knowledge and cannot grant new mathematical support. New mathematical claims return to knowledge and readiness work. Semantic review, actual compilation and every-page review bind the actual report revision; failed attempts and prior revisions remain visible. Compiler inputs are isolated; finding dependencies or tools is not evidence of successful rendering.

The interface uses stable translation keys with English fallback and a host-persisted `ui_locale`. Translation changes display only, retaining English research/report constraints, exact identifiers and frozen contracts. Polling refreshes tasks, actions, retrieval and reports while preserving the reading body. Three workflow diagrams show the selected instance and main paths by default, with every registered legal path available on demand and explicit structure previews for unloaded workflows.

See [scope](ACCEPTANCE-SCOPE-4.2.0.md), [4.2.0 validation and historical provenance](TEST-REPORT-4.2.0.md) and the [bilingual usage guide](README.md).

## Project assistant

The unified Web panel binds a native project conversation to project, task/request or exact report context. Its PROJECT_ASSISTANT purpose is separate from scientific stages and uses gpt-6-astra/xhigh with capability checks and no silent fallback. Opening, reading history and polling make no model call. Initial assistant allowance is zero; explicitly authorized assistant and report work share the same native request/capture recovery and project/host pool, without spending or extending research authorization.

Diagnosis consumes bounded native status, request/receipt identities and selected report failures/checks, with facts, inferences, unknowns and advice kept distinct. An explicit report revision binds the original human instruction, profile, old revision/raw-body hash and knowledge snapshot. Immutable references supply the actual old draft, cumulative effective requirements and explicitly referenced suggestions. Deterministic top-level section splicing preserves unselected source bytes; whole-report scope must be explicit. Authors, renderers, semantic checks and all-page visual checks produce the new native version while retaining old versions. Additional finite report allowance resumes the original action and future roles without repeating an accepted author request. Paused research stays paused; UNKNOWN remains evidence-dependent. The panel is not a new researcher, human decision-maker or general system operator.

## Bounded task preparation

Native input preparation counts local immutable file sizes and unique hashes before reading bodies. Unique material plus scoped record/source metadata is limited to 32 MiB, with an 8 MiB metadata sublimit; packet and complete request serialization are each bounded at 64 MiB. These storage limits supplement the independently frozen model token capacity and output reserve. An oversized complete input is rejected before model dispatch; it is never silently truncated. Explicit coverage parts retain their declared original hashes and checked boundaries within the supported input budget.

New packets use immutable hash references for selected material bodies and report files; task materialization writes one readable copy at a time with 256 KiB copy chunks and hash verification. Packets do not duplicate these bodies as inline text or base64. The exact required closure includes premises and relevant reverse evidence, rather than the entire available library. Model input accounting includes the actual presented material and frozen output reserve. The copy fallback creates independent files, never writable hard links to authoritative blobs. Visual tasks receive the relevant manuscript, actual pages and neighboring-page context with a small identity manifest; they do not duplicate the literature corpus. Author and semantic roles retain their complete necessary evidence. Earlier frozen packets remain readable without rewriting their bytes or identities.

Resource reservations use a shared, process-identified, OS-locked ledger. Per-phase estimated memory is 256 MiB for preparation, 96 MiB for a client, 256 MiB for capture, 512 MiB for admission and 1,024 MiB for rendering. At most two preparations, or the lower existing project concurrency, may hold short preparation slots. Admission compares outstanding estimates with available physical memory and a safety margin. Temporary disk reservations are counted together on the same filesystem, with at most 512 MiB per reservation and 512 MiB free-space margin; task execution reserves 256 MiB and checks its working-directory size. Retained working evidence can preserve its disk reservation after a process exits, while physical-memory reservations expire with that process. Resource shortages preserve the original request and require waiting, a narrower explicit scope or sufficient resources; they never authorize resending an uncertain call.

The retained workflow/resource development measurement covered eight 1 MiB tasks, a separate 8 MiB task and a real one-page render overlap: sampled process-tree RSS peaked at 379.4 MiB, and preparation at 144.2 MiB. A separate 30 MiB single-task case peaked at 95.8 MiB. There were no paid model calls or network requests. These 20 ms RSS samples can miss short peaks and double-count shared pages; synthetic token allowances are not real-model capacity claims. The estimates are not added OS memory or swap limits, and the render measurement does not prove a bound for arbitrary TeX. See [measurement provenance and limitations](IMPLEMENTATION-NOTES-4.2.0.md).

Only a settled task with a verified original capture seal may discard its named, reconstructible input copies. Captures, responses, commands, logs, scientific records, original sources and report evidence remain. Prepared, in-flight and UNKNOWN requests retain their work materials. Cache cleanup failure cannot undo settlement or authorize another model call.
